# Data compatibility and financial integrity

- **Existing CheckoutRecord:** Historical `method: cash`, `gcash` and `bank-transfer` values remain accepted even when the corresponding current Admin method is renamed or deactivated. Such old records do not falsely acquire a new method-name snapshot.
- **New CheckoutRecord:** Uses the existing `method` identifier plus optional `methodId`, `methodNameSnapshot`, and `methodBehaviorSnapshot`. The snapshot freezes the method name and Cash/Noncash semantics at recording time; model validation accepts valid historical snapshots independently of the live directory.
- **Existing ChargePayment:** Previously recorded payments with no method metadata remain valid, with no retroactive attribution. Checkout payment allocations also remain valid without separate method metadata; the authoritative CheckoutRecord contains the settlement method.
- **New individual ChargePayment:** Captures immutable method ID, historical name, behavior and (for Cash) exact tender and change. The source charge amount and original Restaurant/Service identities are not changed.
- **Immutable financial amounts:** Both Checkout and individual-charge payment validations continue to check safe integer centavos, current charge associations and single payment per charge. Configuring or renaming a method cannot recalculate any historical total.
- **No new operational IndexedDB version:** The Checkout and ChargePayment optional fields are backward-compatible within the existing operations store schema v5. Payment-method configuration is a separate versioned browser-local directory.
- **Cross-store limitation:** Front Desk rechecks payment configuration at confirmation and prevents stale selection when it detects revision changes. A localStorage config write and an IndexedDB settlement cannot be committed in one atomic cross-store transaction. Real multi-user payment operation requires server-side authorization and atomic validation.
- **Local concurrency:** Payment-method configuration uses best-effort revision checks. Browser localStorage read-then-write is not an atomic compare-and-swap, and different devices do not share a database. Browser-local controls do not provide production-grade financial integrity.
- **No destructive upgrade:** Invalid stored configuration is reported; old guest-stay, Checkout, order, payment and room-posting records are preserved. No operational database reset is performed.
