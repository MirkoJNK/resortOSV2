# Data and compatibility

- **Room identity:** Administration Rooms Manager remains authoritative using `resortos:rooms-manager:v1` in localStorage. No Front Desk room directory is created. Source-supplied sample rooms are explicitly identified as sample configuration in the UI; they are not verified live occupancy.
- **Guest-stay identity:** `GuestStay` contains immutable `id`, immutable `roomId`, normalized guest name, check-in date, expected checkout date, recorded timestamp, active/checked-out state, creation/update timestamps and optional future checkout timestamp. Only the active state is created by this release. No checkout controls exist.
- **Storage upgrade:** existing `resortos:restaurant-operations:v1` IndexedDB database v2 → v3, adding object store `guest-stays`. Old sessions/orders/reservations/settlements are retained and read with optional legacy fields. The commit path uses one versioned, revision-checked readwrite transaction across all five data stores and revision metadata.
- **New room postings:** demo settlements refer to order ID, dining session ID, immutable room ID, stay ID, amount snapshot and date. Checkout and real payment functionality remain absent.
- **Legacy room postings:** `stayId` remains optional for old records; no historical room-only record is automatically attributed to a current guest. These records remain available in Restaurant Order History.
- **Charge details:** use immutable recorded-line snapshots and partial-removal events. Current-stay demo total sums only valid postings explicitly associated with the active stay. Cash demo settlements are excluded.
- **Concurrency:** optimistic revision checks reject duplicate/stale in-browser edits within this database. Admin room configuration uses a different localStorage source and therefore cannot be locked atomically together with IndexedDB; an Admin configuration change racing exactly with a check-in or posting remains a limitation. Shared server-side transactional integrity and proper authorization are required for real hotel use.
- **Privacy:** the prototype stores guest names in browser-local storage, with no authentication/encryption-at-rest guarantees. Use test names only.
